# Plan: configurable multiline containers

## Goal

Add separate formatting controls for the physical layout of newly generated inline arrays and inline tables. Callers should be able to choose between a compact one-line value and a value with one structural row per line without changing whether an object becomes a TOML section.

The selected regression describes the first required case. When a new object is added as an element of an already multiline array, its fields should be written as a multiline inline table:

```toml
values = [
    {
        name = "new",
        enabled = false
    },
]
```

The same rule must work for arrays nested inside tables, tables nested inside arrays and deeper combinations of both.

## Current behavior

`inlineTableStart` controls the TOML representation chosen for tables. It decides whether a table is emitted as an inline table or as a separate `[table]` or `[[table]]` block. It does not control line layout inside an inline table.

The current generators therefore create compact inline containers by default. A new object
inside a multiline array is generated as a single-line `{ ... }` value even when its
parent already has one item per line. The two regression tests in
`src/__tests__/patch.indentation.test.ts` are marked with `test.fails()` for this reason.

The only case where element inside a table would be inserted as seperate lines is if the
original was already showing that it was intended to be multiline. eg.:
```toml
value = {
}
```

The existing indentation work already provides useful pieces for this feature:

- `TomlFormat.indentWidth` supplies a fallback indentation step for generated rows.
- `useTabsForIndentation` controls the token used for newly generated structural indentation.
- `prepareInsertedNestedInlineContainer()` copies row positions from a comparable multiline sibling.
- The writer preserves source locations and comments rather than reformatting the whole document.

The new option should build on those pieces. It should not make `inlineTableStart` responsible for two unrelated decisions.

## Scope

This plan covers:

- new inline arrays generated by `stringify()` or `patch()`;
- new inline tables generated by `stringify()` or `patch()`;
- generated nested arrays and tables inside existing multiline containers;
- whole-value replacements that create a new inline array or table;
- indentation, tabs, comments, commas and bracket spacing for those generated rows;
- format validation, public types and documentation;
- exact-output and parse-round-trip tests.

This plan does not change:

- the meaning of `inlineTableStart`;
- existing source nodes that patch does not replace;
- the contents of multiline strings;
- conversion of root arrays of objects into `[[array-of-tables]]` blocks;
- a global reformatter or a maximum line-width policy;
- the order of keys inside an inline table unless an existing option already controls that operation.

## Proposed API

Introduce a shared public type for the two new options:

```typescript
type MultilineContainerMode = boolean | number | 'auto' | 'nested';
```

Add these optional format properties:

```typescript
class TomlFormat {
  multilineTable: MultilineContainerMode;
  multilineArray: MultilineContainerMode;
}
```

The properties should follow the existing `TomlFormat` conventions. They should be accepted by `validateFormatObject()`, merged by `resolveTomlFormat()` and available through partial format objects passed to `stringify()` and `patch()`.

### Meaning of each value

| Value | Meaning |
|---|---|
| `true` | Write every newly generated non-empty container of that kind in multiline form. An empty generated container also uses separate opening and closing lines. |
| `false` | Prefer a single-line container whenever TOML permits it. This is an explicit override, including for nested containers. |
| `number` | Write the container in multiline form when its structural container depth is greater than or equal to the number. `0` selects every depth. A value larger than the deepest container selects none. |
| `'auto'` | Currently means that we insert new inline table/array in compact form. This is the default. We want to leave this auto mode in case we implement a `maxPrintWidth` property. The `auto` value would respond to  `maxPrintWidth` unlike `false` |
| `'nested'` | Write the parent container is itself multiline |

`undefined` or `null` means that the caller did not provide a value and should use the `auto` format.

Add the properties at the end of any positional `TomlFormat` constructor arguments so existing constructor calls keep their meaning. Prefer a named or partial format object for new examples. Update generated declarations if the build emits them.

## Depth and terminology

The two new options need one depth definition. Use structural value nesting, not the dotted-key depth used by `inlineTableStart`.

- A root-level inline array or inline table has depth `0`.
- A container used as a value inside another inline container has depth one greater than its parent.
- An object used as an element of `values = [ ... ]` has depth `1`.
- An array used as a property of an inline table has depth `1`.
- Each further inline array or table boundary adds one level.

For example, with `multilineTable: 1`, the outer table remains compact while its nested table values become multiline. With `multilineTable: 0`, all generated inline tables become multiline. The same rule applies independently to `multilineArray`.

`inlineTableStart` keeps its current table-key depth semantics. A table converted to `[section]` or `[[array]]` is no longer an inline table, so `multilineTable` has no role in that block conversion.

## Resolution rules

Resolve a mode at the point where a generated container is created. The resolver should receive the container kind, its structural depth and local layout context.

Use this order:

1. An explicit boolean or numeric mode decides directly.
2. `'nested'` checks whether the structural depth is greater than zero.
3. `'auto'` examines the nearest applicable layout evidence.
4. If no local evidence applies, `'auto'` chooses a single-line representation.

For `'auto'`, use the following working rules:

- A generated container inside a multiline parent inherits multiline layout when it has structural rows to emit.
- A generated container with a comparable multiline sibling copies that sibling's multiline decision and row shape.
- A generated container replacing a multiline value keeps the replaced value's multiline layout when its new kind is compatible.
- A generated root-level container with no multiline sibling or parent remains compact.
- An empty generated container stays `{}` or `[]` under `'auto'` unless a multiline parent or a comparable template requires multiline layout.

These rules produce the selected output because `values` is already a multiline array and the new object is a nested container with multiple fields. They also avoid changing ordinary compact `stringify()` output merely because the new option exists.

The resolver should return a concrete layout decision rather than making the writer interpret the public union repeatedly. A small internal result can carry:

```typescript
interface InlineLayoutDecision {
  multiline: boolean;
  depth: number;
  rowIndent?: string;
  parentIndent?: string;
}
```

The exact internal shape can follow the existing writer metadata style. It must not become part of the public API.

## Interaction with existing options

### `inlineTableStart`

Keep the two decisions separate:

1. `inlineTableStart` decides whether an object is an inline value or a block table.
2. `multilineTable` decides whether an object that remains an inline value is compact or multiline.

Examples:

```typescript
patch(source, value, { inlineTableStart: 0, multilineTable: true });
```

This keeps tables inline but writes their fields on separate lines.

```typescript
patch(source, value, { inlineTableStart: 1, multilineTable: true });
```

This still writes eligible root objects as `[section]` blocks. The option affects only inline tables that remain inside values such as arrays or table rows.

`multilineArray` must not turn an array of objects into an array-of-tables block. That decision remains with the existing formatter.

### `indentWidth` and `useTabsForIndentation`

A multiline decision creates rows. Existing local row evidence should choose their absolute columns using the current precedence:

1. a comparable surviving sibling row;
2. the enclosing container's established local row style;
3. the closing delimiter and `indentWidth` fallback.

When `useTabsForIndentation` is true, generated structural indentation uses tabs. When it is false, generated structural indentation uses spaces and `indentWidth` supplies the number of spaces per level. Explicit format values control new structural rows only. They must not rewrite untouched rows or value text inside multiline strings.

The implementation must keep the indentation of a nested generated table relative to its array element. For the selected two-space default, the outer item and its fields should use separate levels:

```toml
values = [
  {
    name = "new",
    enabled = false
  },
]
```

A four-space or tab-indented source should use the same local unit without converting string content.

### `trailingComma`

A multiline container has two independent comma decisions:

- the comma separating the container from its siblings in the parent;
- the comma separating rows inside the new container.

Keep these decisions independent. A trailing comma on an outer array item must not force a trailing comma inside a newly generated inline table. Existing sibling style should win when patching an existing container. The explicit format should control a newly generated container when no sibling evidence exists.

### `bracketSpacing`

Bracket spacing applies to compact containers. A multiline container should put its opening delimiter on the opening line and its closing delimiter on its own structural line, with no compact spacing token treated as a content row. Existing delimiter-line comments must keep their ownership and columns.

### Newlines and trailing newlines

Use the resolved `newLine` for generated rows. Keep `trailingNewline` as a document-level setting. Choosing multiline layout must not add an extra blank line outside the generated container.

## Layout model

Generate the same CST value shape for both modes, then apply a layout decision before insertion or replacement. This keeps semantic generation separate from physical placement.

### Inline arrays

For a multiline inline array:

- put the opening `[` at the container's existing start position;
- put each `InlineItem` on its own structural row;
- place nested multiline values relative to that item's row;
- put `]` on the closing row unless the source layout supplies a compatible closing position;
- preserve the parent item's comma separately from commas inside nested values.

Support scalar rows, nested arrays, inline-table elements, multiline strings and mixed element types. A scalar multiline array is still an inline array. It must not be confused with a table array.

### Inline tables

For a multiline inline table:

- put the opening `{` at the key-value's value position;
- put each key-value item on its own structural row;
- use the table row indentation for all direct fields;
- lay out nested arrays and tables relative to their field row;
- put `}` on the closing row;
- preserve dotted-key spelling and spacing unless the patch operation already changes that key.

The table may contain comments and dotted keys. The layout code must not assume that the immediate CST parent owns every physical comment row because multiline inline-container comments can be hosted by the enclosing document or table.

### Empty containers

Define the output for an explicit multiline mode so it is stable and testable:

```toml
config = {
}

values = [
]
```

`'auto'` should keep empty generated values compact unless their parent or a comparable template is multiline. Existing empty containers retain their source layout when patching them.

### Existing containers and replacements

Patching an existing multiline array or table should preserve its physical layout when adding or editing members, regardless of the default mode. The new mode applies when:

- the member itself is newly generated;
- an existing value is replaced by a newly generated container;
- a removed container is recreated during the same patch.

A replacement should inherit the replaced row's indentation and local delimiter context before falling back to the resolved document format. It should not reformat unrelated siblings.

## Likely implementation points

### `src/toml-format.ts`

- Add `MultilineContainerMode` and the two format fields.
- Add defaults for both fields.
- Extend format validation to accept booleans, non-negative integers, `'auto'` and `'nested'`.
- Include the fields in `resolveTomlFormat()` without changing the meaning of existing constructor arguments.
- Add unit tests for defaults, partial formats, `null` and `undefined` fallback and invalid values.

### `src/parse-js.ts` and `src/generate.ts`

- Pass container depth and the resolved format into recursive value generation.
- Keep generation of scalar values unchanged.
- Mark generated inline arrays and tables with the requested layout decision before they are inserted.
- Ensure the root value starts at depth `0` and recursive values increment depth exactly once per inline container boundary.
- Keep the existing conversion of eligible root objects and arrays into table sections or table arrays.

### `src/inline-layout.ts`

- Extend the current nested-container preparation code with a shared mode resolver.
- Reuse comparable sibling templates when the mode is `'auto'`.
- Calculate direct-row indentation from local evidence before using `indentWidth`.
- Lay out empty generated containers when an explicit mode selects multiline output.
- Preserve a container's own row columns when a parent has a different indentation style.

### `src/patch.ts`

- Carry the resolved multiline modes through the diffing and generation paths.
- Pass the original node, replacement row and enclosing container into layout resolution where available.
- Apply explicit format modes only to newly generated or replaced inline containers.
- Keep the existing comment-host and pending-offset handling intact.
- Check the path that regenerates a value after an inline-table trailing-comma mismatch. The rebuilt value must receive the same multiline decision as the original generated value.

### `src/writer.ts` and `src/to-toml.ts`

- Confirm that multiline locations can be emitted without relying on stale coordinates from the compact form.
- Keep indentation conversion out of multiline string content.
- Verify that opening and closing delimiter writes do not overwrite comments hosted by an enclosing container.
- Add an internal assertion or focused test if a multiline decision reaches the writer without valid row locations.

### Documentation

- Document both fields in `docs/Formatting.md` with the accepted values and examples.
- Link to this plan from the formatting documentation if the repository's documentation style supports plan links.
- Update any generated API or declaration documentation produced by the build.

## Testing plan

### Format contract tests

Add tests in `src/__tests__/toml-format.test.ts` for:

- default mode is `'auto'`;
- partial objects merge each new property independently;
- `true`, `false`, zero and positive integer values are accepted;
- `'auto'` and `'nested'` are accepted;
- negative numbers, fractional numbers, `NaN`, strings outside the accepted literals and unrelated objects are rejected or warned according to the existing format contract;
- `TomlFormat` constructor compatibility remains intact;
- `resolveTomlFormat()` preserves an explicitly supplied mode over auto-detected fallback values.

### Stringify tests

Add exact-output tests for each mode:

- root-level array with scalar values;
- root-level object that remains an inline table under `inlineTableStart: 0`;
- an object nested in an array;
- an array nested in an inline table;
- two levels of arrays and tables;
- empty arrays and empty tables;
- `multilineTable: 0`, `1` and a value above the maximum depth;
- `multilineArray: 0`, `1` and a value above the maximum depth;
- `'nested'` compared with numeric threshold `1`;
- `'auto'` with no multiline context and with an existing multiline parent;
- interaction with `inlineTableStart: 0`, `1` and a larger threshold.

Every test should assert the complete string and then assert that `parse(result)` equals the original JavaScript value.

### Patch tests

Remove `test.fails()` from the two selected tests only after the implementation produces their exact expected output. Keep the full-output assertions and parse round trips.

Add focused regressions for:

- appending a new object to an existing multiline array;
- prepending and inserting a new object before a surviving sibling template;
- adding fields to a new empty table nested in an array;
- adding an array to a new empty inline table;
- replacing a scalar with a multiline array;
- replacing a scalar with a multiline inline table;
- deleting all members and then adding one back;
- nested arrays containing nested tables;
- multiline containers with and without trailing commas;
- comments before, between and after generated rows;
- comments hosted by an enclosing table rather than the inline container;
- dotted keys inside a multiline table;
- multiline basic and literal strings inside generated containers;
- two-space, four-space and tab indentation;
- an explicit `useTabsForIndentation` override against a differently styled source;
- `indentWidth` overrides for empty and nested generated containers;
- CRLF output and trailing-newline settings;
- `updateOrder: true` combined with a multiline replacement.

Use `dedent` for readable fixtures where that matches neighboring tests. Keep expected TOML comparisons exact. Do not reduce these tests to `toContain()` checks because the feature controls row placement and delimiter lines.

### Fuzz and integration checks

Add at least one fuzz seed for each transition below:

- compact parent to multiline child;
- multiline parent to generated nested array;
- removal followed by reinsertion of a multiline child;
- replacement after a comment was hoisted from an inline container;
- a generated table whose inner comma preference differs from the outer array preference.

For every seed, verify both:

```typescript
expect(parse(patch(source, updated, format))).toEqual(updated);
```

and the exact expected layout when the seed is a style regression.

After implementation, run the repository checks that cover the public output:

- `pnpm run typecheck`;
- `pnpm run build`;
- `pnpm run test`;
- `pnpm run test:all` when browser output or generated artifacts change;
- `pnpm run specs` to confirm that every generated document remains valid TOML.

## Implementation phases

### Phase 1: define and validate the format contract

Add the shared mode type, defaults, validation and format resolution. Add unit tests before changing layout behavior. This phase should leave existing output unchanged.

### Phase 2: resolve mode from structural context

Add one internal resolver that receives container kind, depth, parent layout, sibling templates and replacement context. Keep `'auto'` conservative and encode the selected regression as a failing test until the resolver can explain why the nested table is multiline.

### Phase 3: lay out generated values

Extend `parseJS` and `inline-layout` so generated arrays and tables can be positioned as multiline values. Start with a scalar array and an object inside an existing multiline array. Then add nested combinations and empty containers.

### Phase 4: integrate patch replacements

Thread the decision through new-member insertion, whole-value replacement, recreated containers and the trailing-comma regeneration path. Check pending offsets and comment hosts after each change.

### Phase 5: document and broaden regression coverage

Update `docs/Formatting.md`, remove the selected `test.fails()` markers, add exact-output regressions for indentation, comments and strings then run the full validation suite.

## Open questions

1. Should `'auto'` make a nested child multiline solely because its parent is multiline, or only when the child has more than one structural row? The selected regression requires at least the latter rule.
2. Should a numeric mode use structural value depth as proposed here, or reuse the key-path depth used by `inlineTableStart`? Separate definitions are clearer because arrays do not have table keys, but both need explicit tests.
3. When a new container has no sibling template but its parent mixes compact and multiline children, should `'auto'` use the nearest same-kind sibling or the parent-wide majority? The nearest same-kind sibling is the safer choice.
4. Should `true` force empty generated containers onto separate lines? This plan says yes so the option has a complete meaning, but the output needs a compatibility review.
5. Should a multiline inline table with one scalar field use a trailing comma when the surrounding array is multiline? The inner comma must remain independent from the parent separator.
6. Should callers eventually be able to configure a maximum line width for `'auto'`? That is outside this feature. Do not infer it from viewport width or add an unrequested option.

## Completion criteria

This work is complete when:

- both selected regression tests pass without `test.fails()`;
- `multilineTable` and `multilineArray` accept the documented values and appear in the public format type;
- `inlineTableStart` still controls sections independently from physical inline layout;
- default `'auto'` keeps ordinary compact output while inheriting a clearly multiline local context;
- explicit booleans and numeric thresholds produce deterministic layouts at every tested depth;
- empty containers have documented output for explicit multiline modes;
- generated rows preserve local spaces, tabs, comments, commas and delimiter positions;
- multiline string content remains unchanged unless its value changes;
- replacements do not reindent unrelated source nodes;
- every new exact-output fixture round-trips through `parse()`;
- typecheck, build and tests pass, with specs and browser tests run when their artifacts are affected;
- `docs/Formatting.md` describes the final behavior rather than the implementation plan.
